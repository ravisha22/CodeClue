Click appears to build the CLI in two phases: decoration time creates `Command`-like objects around Python callables, and runtime context creation plus group resolution decides which command/subcommand to invoke.

1. **Decoration turns a Python function into a command object.** The strongest direct clue is `command` in `src/click/decorators.py`, which says it "Creates a new :class:`Command` and uses the decorated function as" the underlying callable, with signature `command(name, cls)` and `UNWIND(reversed)` behavior. That indicates the decorator wraps the function in a `Command` object and processes accumulated decorator state in reverse order while doing so. (`command`, `src/click/decorators.py:168-255`)

2. **Parameter decorators attach metadata before command creation.** The `option` decorator explicitly "Attaches an option to the command," and `_param_memo` exists alongside the decorators machinery, which supports the idea that decorator-applied parameter definitions are memoized and then consumed when the command object is created. (`option`, `src/click/decorators.py:352`; `_param_memo`, `src/click/decorators.py:314`)

3. **The resulting `Command` object is the base executable unit.** `Command` is described as "the basic building block of command line interfaces," and it owns the machinery for context creation, help, and shell-completion entrypoints. It calls `get_params`, `get_help_option`, and other formatting/execution-adjacent methods, and `make_context` is called by `Command`. (`Command`, `src/click/core.py:873-1485`; `make_context`, `src/click/core.py:1182-1217`)

4. **Nested CLIs come from `Group`, which is a specialized `Command`.** `Group` "is a command that nests other commands (or more groups)," so the nesting model is object-based: a group contains subcommands, and those subcommands can themselves be groups. (`Group`, `src/click/core.py:1503-1951`)

5. **Subcommands are registered onto a group, with chain-safety checks.** `Group` calls `add_command`, and `_check_nested_chain` is called by `Group`, `add_command`, and `CommandCollection`; it guards nested-chain validity and can raise `RuntimeError`. That implies when commands/groups are added into a hierarchy, Click validates that the nesting/chain configuration is legal before registering them. (`Group`, `src/click/core.py:1503-1951`; `_check_nested_chain`, `src/click/core.py:73-90`)

6. **The hierarchy can be static or dynamically provided by lookup methods.** The clue index shows example groups exposing `get_command` and `list_commands` (for example `AliasedGroup` and `ComplexCLI`), while core `list_commands` returns subcommand names "in the order they should appear" and delegates to `sorted` by default. So a nested CLI is represented as a group/subcommand tree, but command lookup/listing can be customized by group implementations. (`examples/aliases/aliases.py:get_command, resolve_command, AliasedGroup`; `examples/complex/complex/cli.py:get_command, list_commands, ComplexCLI`; `list_commands`, `src/click/core.py:1784-1786`)

7. **At runtime, Click starts by building a context from argv-like input.** `make_context(info_name, args, parent)` says it "when given an info name and arguments will kick" off processing, accumulates in a loop, and uses `scope`; it is called by both `Command` and `Group`. This indicates runtime dispatch begins by converting the current command name plus remaining arguments into a `Context` object. (`make_context`, `src/click/core.py:1182-1217`; `scope`, `src/click/core.py:496-531`)

8. **Groups keep unconsumed arguments available for subcommand dispatch.** `Group` differs from `Command` in its attributes: `allow_extra_args=True` and `allow_interspersed_args=False`, while plain `Command` defaults to `allow_extra_args=False`. From the clue file alone, that strongly suggests a group accepts additional trailing tokens because they are intended to identify and feed a subcommand rather than being rejected at the current level. (`Group`, `src/click/core.py:1503-1951`; `Command`, `src/click/core.py:873-1485`)

9. **Dispatch to the next command level happens by resolving the subcommand name and creating a subcontext.** `Group` calls `_make_sub_context` and `_process_result`, while `fail` in `src/click/core.py` is called by `resolve_command` and `Group`. Even though the body of `resolve_command` is not shown, those clues together imply the runtime path is: parse current group arguments, resolve the next command token to a registered subcommand, create a child context for it, and then process the result. (`Group`, `src/click/core.py:1503-1951`; `fail`, `src/click/core.py:718-724`; `examples/aliases/aliases.py:resolve_command` in index)

10. **Unknown or invalid dispatch paths surface as usage errors.** `fail(message)` in core "Aborts the execution of the program with a specific error," raises `UsageError`, and is called by `resolve_command` and `Group`. So if subcommand resolution fails, the dispatch path terminates through Click's usage-error mechanism. (`fail`, `src/click/core.py:718-724`)

11. **The same recursive pattern explains multi-level nesting.** Because `Group` itself extends `Command` and can nest "other commands (or more groups)," and because `make_context` is used by both `Command` and `Group`, the most supportable reading is recursive dispatch: each group resolves one command name, creates a subcontext, and either executes a leaf `Command` or repeats the process if the chosen subcommand is another `Group`. (`Group`, `src/click/core.py:1503-1951`; `Command`, `src/click/core.py:873-1485`; `make_context`, `src/click/core.py:1182-1217`)

12. **What cannot be proven from the clue file:** the exact internal data structures used to store registered commands, the exact callback invocation method on `Command`, and the exact token-by-token algorithm inside `resolve_command` / `_make_sub_context` are not exposed here. The clue file itself marks "MECHANISTIC (body logic needed for full answer)" gaps, and it does not include focused entries for `resolve_command` or `add_command` bodies. (`-- GAPS`, clue file; `Group`, `src/click/core.py:1503-1951`; `_check_nested_chain`, `src/click/core.py:73-90`)

**Bottom line:** based solely on the clue file, Click decorates a Python function into a `Command` object (`command`), accumulates option/parameter metadata via decorators such as `option`, organizes commands into recursive `Group` objects via `add_command`, then at runtime builds a `Context` from the incoming args (`make_context`), resolves the next subcommand name (implied by `resolve_command`/`fail`), creates a subcontext (`_make_sub_context`), and repeats until the selected leaf command is the one dispatched. (`command`, `src/click/decorators.py:168-255`; `option`, `src/click/decorators.py:352`; `Group`, `src/click/core.py:1503-1951`; `make_context`, `src/click/core.py:1182-1217`; `fail`, `src/click/core.py:718-724`)
