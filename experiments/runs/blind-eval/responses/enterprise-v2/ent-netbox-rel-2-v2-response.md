### Step 2: Trace the authentication flow for API requests

1. **Token issuance**: Users create API tokens via the UI at `path:api-tokens/add/` (`account/urls.py`, FOCUS), which creates a `UserToken` (`account/models.py`, INDEX). Token values are generated by `generate` (SYM: `netbox/users/models/tokens.py:256`).

2. **API authentication**: Incoming API requests are authenticated by `TokenAuthentication` (FOCUS: `netbox/netbox/api/authentication.py:19-122`), which extends DRF's `BaseAuthentication`. It enforces **token expiration times** and **source IP restrictions**, raising `AuthenticationFailed` or `DoesNotExist` when checks fail. This is the primary authentication class for all API calls.

3. **API permissions**: After authentication, `TokenPermissions` (FOCUS: `netbox/netbox/api/authentication.py:125-169`) validates the token's write ability by extending `DjangoObjectPermissions`. It calls `__init__`, `_verify_write_permission`, and `has_object_permission`. This means even a valid token may be read-only if it lacks write ability — authorization is token-scoped, not just user-scoped.

4. **Specific action overrides**: Some API views override `get_permissions` to require `TokenWritePermission` for specific actions:
   - `RenderConfigMixin.get_permissions` (FOCUS: `netbox/extras/api/mixins.py:70-74`): GUARD returns `[TokenWritePermission]` for `render_config` action.
   - `ConfigTemplateViewSet.get_permissions` (FOCUS: `netbox/extras/api/views.py:243-247`): GUARD returns `[TokenWritePermission]` for `render` action.

5. **Authentication check endpoint**: `path:api/authentication-c` → `AuthenticationCheckView.as_view` (FOCUS: `netbox/netbox/urls.py`) provides a dedicated endpoint to verify whether a request is authenticated, distinct from the regular API routes.

## Synthesized Answer

**Authentication** in NetBox uses a **token-based scheme for the API** and **session-based (Django) authentication for the UI**. The two share a common object-permission backend (`get_all_permissions` / `get_object_permissions`, FOCUS: `netbox/netbox/authentication/__init__.py`), while the API layer adds token-specific enforcement:

1. **API Authentication** (`TokenAuthentication`, FOCUS: `netbox/netbox/api/authentication.py:19-122`): Validates token existence, expiration, and source IP. Raises `AuthenticationFailed` on failure.

2. **API Authorization** (`TokenPermissions`, FOCUS: `netbox/netbox/api/authentication.py:125-169`): Extends `DjangoObjectPermissions` to also check whether the token has write capability. Specific views can additionally require `TokenWritePermission` for mutating actions (e.g., `render_config`, `render`).

3. **UI Permission checks**: `_check_permission` template tag (SYM: `netbox/utilities/templatetags/perms.py:17`) gates UI rendering. `get_all_permissions` short-circuits to empty for inactive/anonymous users (FOCUS: `netbox/netbox/authentication/__init__.py:73-78`), and `ObjectPermissionMixin` drives object-level grants from `settings.DEFAULT_PERMISSIONS`.

4. **Token management**: Users create and manage tokens via the UI at `account/api-tokens/` or via the REST API (`api/users/`). Token values are generated by `generate` (SYM: `netbox/users/models/tokens.py:256`).

5. **API detection**: `is_api_request` (FOCUS: `netbox/utilities/api.py:71-75`) detects the code path, enabling request routing to specialized error handlers (`handle_rest_api_exception`) that return JSON rather than HTML.

The two surfaces (UI and API) share the same underlying permission model (`ObjectPermission`) but diverge at the authentication layer: session cookies for UI, token-in-header for API.
