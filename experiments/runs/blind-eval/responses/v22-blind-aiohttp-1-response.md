The JSON path is explicit: `request.json()` first awaits `self.text()`, rejects an unexpected mimetype by raising `HTTPBadRequest` when `self.content_type` does not match the expected JSON type, and only then calls `loads(body)`. Because `text()` is built on `read()`, the JSON path ultimately goes through the request-body reader. [source snippet: json (aiohttp/web_request.py L654-671); clue: read (aiohttp/web_request.py:624-643)]

For non-JSON form-style bodies, the evidence shows the request-side body reader is still `read()`: `read()` is what `post` and `text` call, and it is the point that can raise `HTTPRequestEntityTooLarge`. For urlencoded decoding, the provided materials show the form decoder pattern as “read bytes, choose charset, then decode”: `multipart.BodyPartReader.form()` is described as “Like read(), but assumes that body parts contain form urlencoded data,” and it calls `get_charset` plus `read`. [clue: read (aiohttp/web_request.py:624-643); clue: form (aiohttp/multipart.py:475-493)]

For multipart uploads, `request.multipart()` does not eagerly materialize everything; it delegates to `MultipartReader`, so the handler gets an async multipart reader. `MultipartReader` in turn reads boundaries and constructs per-part readers, and each `BodyPartReader.read()` accumulates data by repeatedly calling `read_chunk()` and `decode_iter()`. [clue: multipart (aiohttp/web_request.py:673-680); clue: MultipartReader (aiohttp/multipart.py:639-854); clue: read (aiohttp/multipart.py:304-322)]

Inside each multipart part, `read_chunk()` enforces the low-level mechanics: it reads either by known length or by stream, does extra padding reads for base64 transfer encoding so the chunk length is divisible by 4, tracks `_read_bytes`, marks EOF when the part length is exhausted, and raises `ValueError` if the terminating CRLF is wrong. `decode_iter()` then applies content-transfer decoding first and content decoding second, potentially asynchronously. [source snippet: read_chunk (aiohttp/multipart.py L324-366); source snippet: decode_iter (aiohttp/multipart.py L524-538)]

The multipart writer snippets also show how multipart metadata is interpreted when bodies are constructed: `append_payload()` auto-adds `Content-Disposition: form-data` names for form-data parts, validates content-encoding / transfer-encoding values, and sets `Content-Length` when size is known and no encoding blocks it. [source snippet: append_payload (aiohttp/multipart.py L963-999)]

As for limits, the only enforced request-size guard exposed in the provided materials is `web_request.read()`, which is explicitly marked as raising `HTTPRequestEntityTooLarge` and is upstream of `post` and `text`, so that is the visible payload-limit enforcement point for handler-side body consumption in this evidence set. The supplied materials do not expose a different higher-level limit check for `json()` or `multipart()` beyond that shared read path.
