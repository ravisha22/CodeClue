Shutdown unwinds in two layers: the runner first unwinds server/socket state, then the application unwinds startup/cleanup resources. In `BaseRunner.cleanup()`, it stops sites one by one, and—if setup created `_server`—it yields once to the event loop, calls `pre_shutdown()`, awaits the runner’s `shutdown()` hook, then awaits `self._server.shutdown(self._shutdown_timeout)`. After that, it always calls `_cleanup_server()`. [source snippet: BaseRunner (aiohttp/web_runner.py L252-352)]

For an `AppRunner`, those abstract hooks are wired directly to the application: `shutdown()` awaits `self._app.shutdown()`, and `_cleanup_server()` awaits `self._app.cleanup()`. Startup is the mirror image: `_make_server()` freezes `on_startup`, runs `app.startup()`, freezes the app, and then creates the `Server`. [source snippet: AppRunner (aiohttp/web_runner.py L380-453)]

The application-side unwind is driven by cleanup context bookkeeping. The clue says `_on_startup(app)` has `ACCUMULATE(loop -> exits)`, while `_on_cleanup(app)` has `UNWIND(reversed)` and `ACCUMULATE(loop -> errors)`, and both `CleanupContext` and `_on_cleanup` can raise `CleanupError`. That means startup records exit callbacks as contexts enter, and cleanup runs those recorded exits in reverse order, collecting failures instead of stopping at the first one. [clue: _on_startup (aiohttp/web_app.py:420-428); clue: _on_cleanup (aiohttp/web_app.py:430-441); clue: CleanupContext (aiohttp/web_app.py:415-441); clue: CleanupError (aiohttp/web_app.py:403-406)]

That same structure explains partial initialization. `BaseRunner.cleanup()` only runs the server pre-shutdown sequence when `_server` exists (“If setup succeeded”), but it still calls `_cleanup_server()` afterward. Since `AppRunner._cleanup_server()` is `await self._app.cleanup()`, application cleanup still runs even if the server was not fully created, which is exactly what you want for startup resources that were only partially initialized before failure. [source snippet: BaseRunner (aiohttp/web_runner.py L252-352); source snippet: AppRunner (aiohttp/web_runner.py L380-453)]

`Application.cleanup()` also has a fallback path: the clue says it branches on whether `on_cleanup` is frozen, calling `_on_cleanup` directly otherwise. So even if normal signal freezing/setup did not finish, cleanup can still go through the cleanup-context unwinder instead of depending on the frozen signal pipeline. [clue: cleanup (aiohttp/web_app.py:351-360); clue: _on_cleanup (aiohttp/web_app.py:430-441)]

If multiple cleanup steps fail, they are accumulated and then surfaced as `CleanupError`, rather than being silently dropped or short-circuiting after the first failure. That behavior is directly stated by `_on_cleanup`’s `ACCUMULATE(loop -> errors)` plus `raises: CleanupError`, and by `CleanupContext` also being marked as raising `CleanupError`. [clue: _on_cleanup (aiohttp/web_app.py:430-441); clue: CleanupContext (aiohttp/web_app.py:415-441); clue: CleanupError (aiohttp/web_app.py:403-406)]
