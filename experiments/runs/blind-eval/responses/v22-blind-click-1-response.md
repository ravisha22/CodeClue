Click first turns decorators into command metadata, then turns that metadata into `Command` / `Group` objects. The decorator side is explicit: `option()` instantiates an `Option` and passes it to `_param_memo`, and `argument()` does the same for arguments. The `command()` decorator then “Creates a new `Command` and uses the decorated function as” the callback, with behavior marked `UNWIND(reversed)`, which means the stacked decorator metadata is unwound in reverse when building the final command object. [source snippet: option (src/click/decorators.py L352-377); clue: argument (src/click/decorators.py:324-349); clue: command (src/click/decorators.py:168-255)]

Nested CLIs come from `Group`, not plain `Command`. The clue states that `Group` “is a command that nests other commands (or more groups),” and that it calls `add_command`, `make_context`, `_make_sub_context`, `fail`, `scope`, and `_process_result`. So once a decorated callback has been turned into a `Group`, it can own subcommands and build nested invocation contexts for them. [clue: Group (src/click/core.py:1503-1951)]

Subcommands are attached through `add_command()`. That method “Registers another `Command` with this group,” and it calls `_check_nested_chain()`. `_check_nested_chain()` enforces one structural rule shown in the snippets: if the parent group is in chain mode and the child is itself a `Group`, Click raises `RuntimeError` instead of allowing unsupported nested chained groups. [clue: add_command (src/click/core.py:1622-1630); source snippet: _check_nested_chain (src/click/core.py L73-90)]

Command lookup and ordering are also group-level concerns. `list_commands(ctx)` returns subcommand names “in the order they should appear,” with behavior `DELEGATE(sorted -> result)`, and the repository examples highlight custom `get_command` / `list_commands` implementations (`AliasedGroup`, `ComplexCLI`). That shows the dispatch layer can either use the default sorted subcommand table or a custom lookup strategy supplied by a `Group` subclass. [clue: list_commands (src/click/core.py:1784-1786); clue: examples/aliases/aliases.py; clue: examples/complex/complex/cli.py]

At runtime, dispatch flows through the group context machinery. The evidence supplied does not show the exact `invoke` / `resolve_command` body, but it does show the pieces `Group` uses: it creates a root context (`make_context`), creates child contexts for nested commands (`_make_sub_context`), and then post-processes results (`_process_result`). So the supported mechanistic reading is: parse into a top-level group context, choose a subcommand from the group’s registered command table / lookup hooks, create that subcommand’s context, then run that command (or group) and process the nested result.
