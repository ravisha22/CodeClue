The provided materials show the non-command-line value path as: choose a fallback value source, then process it, then type-cast it. The selection hook is `consume_value(ctx, opts)`, which the clue explicitly calls out for `Option` and notes that the value can come from an interactive prompt. After a raw value is chosen, `process_value(ctx, value)` handles the `UNSET` vs. present-value branch and can raise `MissingParameter`, and `type_cast_value(ctx, value)` does the actual conversion and validation. [clue: consume_value (src/click/core.py:3256-3318); clue: process_value (src/click/core.py:2416-2480); clue: type_cast_value (src/click/core.py:2342-2396); clue: MissingParameter (src/click/exceptions.py:137-205)]

The materials also show two additional non-CLI sources besides prompts. First, envvar values are supported at the type layer: `split_envvar_value(rv)` exists specifically to split a value coming from an environment variable. Second, defaults are part of the same fallback pipeline because `process_value` has an explicit `value_is_UNSET` branch, i.e. something must decide whether a usable value was found before the missing-parameter error is raised. The exact precedence among prompt/env/default is not exposed in the supplied snippets, but those are the fallback mechanisms visible in this evidence set. [clue: split_envvar_value (src/click/types.py:126-134); clue: process_value (src/click/core.py:2416-2480); clue: consume_value (src/click/core.py:3256-3318)]

Decorated options and arguments participate in that pipeline because both decorators attach parameter objects to the command via `_param_memo`, and `Command.get_params()` returns the command’s parameter list (plus the auto help option if present). So the fallback-value logic applies to the same `Option` / `Argument` objects created by the decorators. [source snippet: option (src/click/decorators.py L352-377); clue: argument (src/click/decorators.py:324-349); source snippet: get_params (src/click/core.py L1002-1025)]

`File` does more than plain scalar conversion. The clue says it is a `ParamType` for reading/writing files and that it calls `resolve_lazy_flag`, `fail`, and `_is_file_like`. The underlying helper is `open_file()`, which adds three special behaviors: `'-'` maps to stdin/stdout, `lazy=True` returns a `LazyFile`, and `atomic=True` writes through a temp/replace flow exposed through `open_stream`. [clue: File (src/click/types.py:754-872); source snippet: open_file (src/click/utils.py L358-404)]

`LazyFile` adds the important deferred-open mechanics. It stores the filename/mode, pre-checks read-mode files by briefly opening and closing them, delays the real open until first access, turns `OSError` into `FileError`, and only closes the wrapped stream when it actually owns that stream. That is why file conversion is more than just “return the string path.” [source snippet: LazyFile (src/click/utils.py L109-194)]

When the stream should stay open—most notably standard streams selected via `'-'`—`open_file()` wraps it in `KeepOpenFile`, whose context-manager `__exit__` is a no-op. So File conversion has to preserve special stream lifetime rules in addition to validating/opening the target. [source snippet: open_file (src/click/utils.py L358-404); source snippet: KeepOpenFile (src/click/utils.py L197-219)]

`Path` does analogous extra work without opening the file. The clue says it is “similar to the `File` type,” but instead of file-opening helpers it calls `fail` and `coerce_path_result(value)`. So its conversion step includes path-specific validation plus coercion of the return value into the desired path representation, rather than merely passing the raw string through.
