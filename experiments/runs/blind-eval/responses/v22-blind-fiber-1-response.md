# Response: blind-fiber-1 (v2.2 fresh)

The provided materials show that a reroute after middleware path rewriting means “run the router again against the new path and the same method tables.” Path matching itself is exposed by `RoutePatternMatch(path, pattern, ...)`, and the request path can be overridden through `DefaultCtx.Path(override ...string)`. Whether the rerun matched is then surfaced by `DefaultCtx.Matched()`, which “returns true if the current request path was matched by the router.” [clue: RoutePatternMatch (path.go:155-155); clue: DefaultCtx.Path (ctx.go:297-297); clue: DefaultCtx.Matched (ctx.go:375-376)]

The router distinguishes middleware registrations from method-specific route registrations. `App.Use`, `Group.Use`, and `domainRouter.Use` all register middleware routes that match a path prefix, while normal handlers are registered per method through `Group.Get`, `Group.Post`, `Group.Put`, etc., or across all methods through `App.All` / `Group.All`. That means when middleware rewrites the path and dispatch restarts, Fiber re-evaluates the rewritten path against those registered middleware and method-specific route patterns. [clue: App.Use (app.go:860-860); clue: Group.Use (group.go:70-70); clue: domainRouter.Use (domain.go:350-350); source snippets: Group.Get / Post / Put / Delete / ...; clue: App.All (app.go:961-961)]

A normal match is therefore the easy case: if the rewritten path matches a registered route pattern for the current method, dispatch proceeds normally and `Matched()` becomes true. That conclusion is directly supported by the combination of method-specific registration APIs plus `Matched()`’s definition. [clue: DefaultCtx.Matched (ctx.go:375-376); source snippets: Group.Get / Post / Put / Delete / ...; clue: App.All (app.go:961-961)]

A 404 is the other clear case supported by the evidence: if the rewritten path does not match any registered route pattern, then the request is still “not matched by the router,” which is exactly the negative case of `Matched()`. [clue: DefaultCtx.Matched (ctx.go:375-376); clue: RoutePatternMatch (path.go:155-155)]

The provided materials do not expose the exact branch body that emits 405, but they do expose the structural reason it can happen: routes are stored per HTTP method (`Get`, `Post`, `Put`, etc.), while `All` is the explicit all-method escape hatch. So the evidence-supported inference is that after restart, if the rewritten path matches a registered route pattern but only under other methods, the request can be treated differently from the “no path matched at all” case—i.e. the classic 405-vs-404 distinction implied by method-specific registration.
