The panic-to-response path starts by normalizing the panic payload into an `error`. The clue for `DefaultPanicHandler` is explicit: if the recovered panic value `r` is already an error it returns that directly; otherwise it creates a new error using `%v`. That gives Fiber an ordinary `error` value to feed into its normal error pipeline. [clue: DefaultPanicHandler (middleware/recover/recover.go:16-16)]

From there, Fiber’s server-facing bridge is `App.serverErrorHandler`. The clue says it is “a wrapper around the application's error handler method ... for the fasthttp server configuration,” and that its body has `UNWIND(defer)` plus `DISPATCH(switch)` behavior while calling `Error` and `NewError`. So server/runtime failures are normalized there and forwarded into application-level error handling. [clue: App.serverErrorHandler (app.go:1411-1411)]

The application-level chooser is `App.ErrorHandler(ctx, err)`. Its clue says it is “in charge of finding the appropriate handler for the given request,” with loop/precedence behavior, which implies error rendering is request-sensitive rather than a single global hard-coded formatter. The default fallback is `DefaultErrorHandler`, which is identified as the handler that processes returned handler errors; related default handlers elsewhere are described as logging the error and sending a 500. The response-writing primitives visible in the clue are `Status`, `SendStatus`, and `SendString`, so the HTTP response is produced by whichever error handler `App.ErrorHandler` selects. Mounted sub-apps can change the formatter because Fiber explicitly integrates them into startup-time routing state. `mountStartupProcess` handles mounted apps by calling `hasMountedApps`, `appendSubAppLists`, `generateAppListKeys`, and `processSubAppsRoutes`. `appendSubAppLists` “supports nested for sub apps,” `processSubAppsRoutes` “adds routes of sub-apps recursively when the server is started,” and `MountPath` exposes the mount route for the current app. That means mounted apps are not opaque children—they are inserted into the app/routing structure used once requests are being served. [clue: App.mountStartupProcess (mount.go:113-114); clue: App.hasMountedApps (mount.go:108-109); clue: App.appendSubAppLists (mount.go:139-139); clue: App.processSubAppsRoutes (mount.go:168-169); clue: App.MountPath (mount.go:103-104)]

Combining those two facts gives the mechanism the evidence supports: a panic is converted into an `error`, `serverErrorHandler` hands it into `App.ErrorHandler`, and because mounted sub-apps are recursively added to the started app’s route/app lists, the “appropriate handler for the given request” can be the mounted app’s handler rather than the parent app’s handler for requests under that mount path. In other words, mounted sub-apps can change which error formatter runs by changing which app owns the request during error handling.
