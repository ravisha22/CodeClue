## Answer
Middleware enters the request-handling pipeline first through registration APIs. `App.Use`, `Group.Use`, and `domainRouter.Use` all register middleware routes, and `Registering.All` also explicitly says it registers a middleware route. Because `Group` is defined as a collection of routes that share middleware and a common path prefix, the clue shows middleware being attached both globally and to nested route groups. (clue: `App.Use`, `app.go:860-860`; `Group.Use`, `group.go:70-70`; `domainRouter.Use`, `domain.go:350-350`; `Registering.All`, `register.go:50-50`; `Group`, `group.go:14-15`)

The route/middleware pipeline is also tied to handler wrapping. `domainRouter.wrapHandlers` explicitly wraps every handler in a slice, which is a strong indication that routing composes handlers/middleware before execution. `App.Use`, `Group.Use`, and `domainRouter.Use` each have control-flow annotations (`PRECEDENCE`, `ACCUMULATE`, `DISPATCH`) and can panic, which further suggests these methods perform nontrivial pipeline construction rather than just storing a single function pointer. (clue: `domainRouter.wrapHandlers`, `domain.go:278`; `App.Use`, `app.go:860-860`; `Group.Use`, `group.go:70-70`; `domainRouter.Use`, `domain.go:350-350`)

The clue gives one explicit "execution pipeline" description in `client/core.go`: `core` "stores middleware and plugin definitions and defines the request execution process," with methods `afterHooks`, `execFunc`, `execute`, `getRetryConfig`, `preHooks`, and `timeout`. That is direct evidence that middleware/hooks are modeled as part of an execution pipeline. (clue: `core`, `client/core.go:48-48`)

Several middleware/adaptor entries show how middleware interacts with request objects and request context during execution. `HTTPHandlerWithContext` calls `HTTPHandler` and `LocalContextFromHTTPRequest`; `ConvertRequest` converts a `fiber.Ctx` to an `http.Request`; `CopyContextToFiberContext` copies values into the request context; and `HTTPMiddleware` wraps `net/http` middleware into Fiber middleware. Together, these entries show middleware being adapted into, and carrying state through, the request pipeline. (clue: `HTTPHandlerWithContext`, `middleware/adaptor/adaptor.go:65-65`; `ConvertRequest`, `middleware/adaptor/adaptor.go:89-89`; `CopyContextToFiberContext`, `middleware/adaptor/adaptor.go:101-101`; `HTTPMiddleware`, `middleware/adaptor/adaptor.go:162-162`)

Other middleware entries show request-scoped effects during or after handling. `Middleware.initialize` in the session middleware "sets up middleware for the request" and takes a `fiber.Ctx`; `FromContext` retrieves that middleware from the Fiber context; `New` in `middleware/skip` returns middleware that evaluates a predicate for each request; `IsFromCache` and `WasPutToCache` report cache-middleware effects on the current request; and `IsEarly` reports whether early-data middleware accepted the request. (clue: `Middleware.initialize`, `middleware/session/middleware.go:111-111`; `FromContext`, `middleware/session/middleware.go:179-179`; `New`, `middleware/skip/skip.go:10-10`; `IsFromCache`, `middleware/idempotency/idempotency.go:29-29`; `WasPutToCache`, `middleware/idempotency/idempotency.go:35-35`; `IsEarly`, `middleware/earlydata/earlydata.go:16-16`)

Finally, the running request context knows whether middleware participated: `DefaultCtx.IsMiddleware` reports whether the current request handler was registered as middleware, `DefaultCtx.Matched` reports whether the path matched the router, and `StoreInContext` writes values to both Fiber locals and request context. That ties middleware state directly to the active request-handling context. (clue: `DefaultCtx.IsMiddleware`, `ctx.go:380-381`; `DefaultCtx.Matched`, `ctx.go:375-376`; `StoreInContext`, `helpers.go:83-83`)
