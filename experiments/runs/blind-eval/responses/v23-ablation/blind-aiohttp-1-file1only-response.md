# v2.3 Ablation (File 1 Only): blind-aiohttp-1
Date: 2026-04-15

The clue file points to one shared body-reading path plus format-specific wrappers.

- The common entry point for consuming request bytes is `read (aiohttp/web_request.py:624-643)`, which “Read[s] request body if present,” is called by `post`, `text`, and `BaseRequest`, and can raise `HTTPRequestEntityTooLarge`. From File 1 alone, this is the clearest place where request-size limits are enforced. (clue: `read (aiohttp/web_request.py:624-643)`)
- JSON goes through a text layer first: `json (aiohttp/web_request.py:654-671)` “Return[s] BODY as JSON,” calls `text`, and can raise `HTTPBadRequest`. Because `read` is called by `text`, the JSON path appears to be `json -> text -> read`, so JSON parsing happens after the normal request-body read/limit path. (clue: `json (aiohttp/web_request.py:654-671)`, `read (aiohttp/web_request.py:624-643)`)
- Multipart is handled differently: `multipart (aiohttp/web_request.py:673-680)` does not eagerly return parsed data, but “Return[s] async iterator to process BODY as multipart” by delegating to `MultipartReader`; it is also called by `post`. (clue: `multipart (aiohttp/web_request.py:673-680)`, `MultipartReader (aiohttp/multipart.py:639-854)`)
- Once in multipart mode, the framework reads part bodies incrementally. `BodyPartReader` is the “Multipart reader for single body part,” with `chunk_size=8192`, and its `read (aiohttp/multipart.py:304-322)` accumulates data by repeatedly calling `read_chunk` and `decode_iter`. That means multipart payloads are processed part-by-part and chunk-by-chunk rather than as one monolithic blob. (clue: `BodyPartReader (aiohttp/multipart.py:257-599)`, `read (aiohttp/multipart.py:304-322)`, `read_chunk (aiohttp/multipart.py:324-366)`)
- For JSON inside a multipart part, `json (aiohttp/multipart.py:467-473)` says it is “Like read(), but assumes that body parts contains JSON data,” and it calls `get_charset` and `read`. So part-level JSON decoding is built on top of the same part-level raw read. (clue: `json (aiohttp/multipart.py:467-473)`, `read (aiohttp/multipart.py:304-322)`)
- For URL-encoded form data at the multipart-part level, `form (aiohttp/multipart.py:475-493)` is also “Like read(), but assumes that body parts contain form urlencoded data”; it branches on encoding, calls `get_charset` and `read`, and may raise `ValueError`. (clue: `form (aiohttp/multipart.py:475-493)`, `read (aiohttp/multipart.py:304-322)`)
- The clue file strongly supports the statement that top-level payload limits are enforced in `web_request.read`, because that is the request-level body reader and the only place in this path explicitly marked as raising `HTTPRequestEntityTooLarge`. By contrast, the multipart part readers are described in terms of chunking/decoding and raise `ValueError`, `RuntimeError`, or iteration-related exceptions, but File 1 does not show a separate multipart-specific size guard there. (clue: `read (aiohttp/web_request.py:624-643)`, `BodyPartReader (aiohttp/multipart.py:257-599)`, `MultipartReader (aiohttp/multipart.py:639-854)`)
- One limitation of File 1: it does not expose the full body of the top-level `post` method, so I cannot prove the exact branching for non-multipart `application/x-www-form-urlencoded` at the request level. What is explicit is that `post` reaches both `read` and `multipart`, and that URL-encoded form decoding definitely exists at the body-part layer via `multipart.form`. (clue: `read (aiohttp/web_request.py:624-643)`, `multipart (aiohttp/web_request.py:673-680)`, `form (aiohttp/multipart.py:475-493)`)
