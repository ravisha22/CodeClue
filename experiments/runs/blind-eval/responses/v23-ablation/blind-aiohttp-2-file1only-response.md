# v2.3 Ablation (File 1 Only): blind-aiohttp-2
Date: 2026-04-15

From File 1, shutdown looks like a staged unwind: stop accepting/serving work, run shutdown hooks, then run cleanup logic that reverses startup-acquired resources and aggregates failures.

- Application startup and cleanup are explicitly paired. `startup (aiohttp/web_app.py:337-342)` “Causes on_startup signal,” and `_on_startup (aiohttp/web_app.py:420-428)` has behavior `ACCUMULATE(loop -> exits)`, which strongly suggests startup registers a sequence of exit/cleanup callbacks or resources to unwind later. (clue: `startup (aiohttp/web_app.py:337-342)`, `_on_startup (aiohttp/web_app.py:420-428)`)
- Shutdown itself is a separate phase before cleanup. `shutdown (aiohttp/web_runner.py:302-303)` says it will “Call any shutdown hooks to help server close gracefully,” while `shutdown (aiohttp/web_server.py:111-114)` is the server-level shutdown entrypoint and `pre_shutdown (aiohttp/web_server.py:107-109)` accumulates over a loop. That implies graceful shutdown first walks active server-side state before final cleanup. (clue: `shutdown (aiohttp/web_runner.py:302-303)`, `shutdown (aiohttp/web_server.py:111-114)`, `pre_shutdown (aiohttp/web_server.py:107-109)`)
- Runner cleanup is then performed afterward. `cleanup (aiohttp/web_runner.py:305-330)` has behavior `ACCUMULATE(loop -> result)` and calls `stop`, and `_cleanup_server` is described as “Run any cleanup steps after the server is shutdown.” So the runner drains its managed resources and only then executes server/app-specific cleanup hooks. (clue: `cleanup (aiohttp/web_runner.py:305-330)`, `_cleanup_server (aiohttp/web_runner.py:337-338)`, `_cleanup_server (aiohttp/web_runner.py:376-377)`, `_cleanup_server (aiohttp/web_runner.py:452-453)`)
- Application cleanup is centralized in `cleanup (aiohttp/web_app.py:351-360)`, which “Causes on_cleanup signal,” branches on `on_cleanup.frozen`, and calls `_on_cleanup`. That branch implies cleanup behavior differs depending on how far initialization/signals progressed. (clue: `cleanup (aiohttp/web_app.py:351-360)`, `on_cleanup (aiohttp/web_app.py:322-323)`)
- The actual unwind order is explicit: `_on_cleanup (aiohttp/web_app.py:430-441)` has behavior `ACCUMULATE(loop -> errors); UNWIND(reversed)`. So cleanup runs in reverse order, which matches the idea that startup had accumulated `exits` in `_on_startup`. (clue: `_on_startup (aiohttp/web_app.py:420-428)`, `_on_cleanup (aiohttp/web_app.py:430-441)`)
- If cleanup only partially initialized, File 1 suggests the framework is designed to cope with that by branching in `cleanup` based on whether `on_cleanup` is frozen and by routing cleanup through `CleanupContext` / `_on_cleanup` rather than assuming all startup steps completed. However, the exact partial-init guard logic is not exposed in the clue file, so this is an evidence-based inference rather than a direct statement. (clue: `cleanup (aiohttp/web_app.py:351-360)`, `CleanupContext (aiohttp/web_app.py:415-441)`, `_on_cleanup (aiohttp/web_app.py:430-441)`)
- If multiple cleanup steps fail, the framework does not appear to stop at the first failure. `_on_cleanup` explicitly accumulates `errors` across the loop and raises `CleanupError`; `CleanupError` is a dedicated `RuntimeError` subclass used by both `_on_cleanup` and `CleanupContext`. That strongly indicates multiple failures are gathered and rethrown as one cleanup-specific exception. (clue: `_on_cleanup (aiohttp/web_app.py:430-441)`, `CleanupError (aiohttp/web_app.py:403-406)`, `CleanupContext (aiohttp/web_app.py:415-441)`)
