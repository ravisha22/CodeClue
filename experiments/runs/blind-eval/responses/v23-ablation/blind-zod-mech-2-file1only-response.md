# v2.3 Ablation (File 1 Only): blind-zod-mech-2
Date: 2026-04-15

File 1 only exposes part of the message-selection story, but the visible precedence is: if an issue already has a message, formatting prefers that issue-level message; otherwise Zod falls back to its default/error-map path; and the final `Error.message` string is just a serialization of the already-chosen issue messages.

- Zod has an explicit error-map abstraction. `ZodErrorMap` is a function type taking `(issue, _ctx)` and returning `{ message: string }`. That means one customization layer is “given this issue and context, compute a message.” (clue: `ZodErrorMap (packages/zod/src/v3/ZodError.ts:329-330)`)
- Issues themselves may already carry a message before formatting. `ZodError.format (packages/zod/src/v3/ZodError.ts:217-264)` uses `issue.message`, and its behavior is `PRECEDENCE(issue -> default)`. That is the clearest message-selection rule visible in File 1: an issue-provided message takes precedence over the default formatting path. (clue: `ZodError.format (packages/zod/src/v3/ZodError.ts:217-264)`)
- Schema/check APIs can supply those issue-level messages. For example, `ZodNumber.multipleOf(value, message?: errorUtil.ErrMessage)` and `ZodBigInt.multipleOf(value, message?: errorUtil.ErrMessage)` both accept an optional message, delegate to `_addCheck`, and use `errorUtil.toString`. That strongly suggests check-level custom messages are converted and attached when the issue/check is created, which would then feed the `issue.message` precedence above. (clue: `ZodNumber.multipleOf (packages/zod/src/v3/types.ts:1547-1554)`, `ZodBigInt.multipleOf (packages/zod/src/v3/types.ts:1792-1800)`)
- Custom issue payloads are also part of the design. `CustomErrorParams` is a partial `ZodCustomIssue` minus `code`, which is more evidence that issue-local error data can be attached before final formatting. (clue: `CustomErrorParams (packages/zod/src/v3/types.ts:55-56)`)
- The top-level `ZodError.message` is not another decision layer. `ZodError.message (packages/zod/src/v3/ZodError.ts:280-282)` simply delegates to `JSON.stringify(this.issues, util.jsonStringifyReplacer)`, and `ZodError.toString` uses `this.message`. So by the time `error.message` is produced, Zod is serializing the issue list; it is not re-running message precedence there. (clue: `ZodError.message (packages/zod/src/v3/ZodError.ts:280-282)`, `ZodError.toString (packages/zod/src/v3/ZodError.ts:277-279)`)
- The practical File-1-only ordering therefore looks like:
  1. a validator/check may attach a custom message when building an issue, (clue: `ZodNumber.multipleOf (packages/zod/src/v3/types.ts:1547-1554)`, `ZodBigInt.multipleOf (packages/zod/src/v3/types.ts:1792-1800)`)
  2. `ZodError.format` prefers `issue.message` over the default path, (clue: `ZodError.format (packages/zod/src/v3/ZodError.ts:217-264)`)
  3. the fallback/default path is represented by the error-map mechanism, (clue: `ZodErrorMap (packages/zod/src/v3/ZodError.ts:329-330)`)
  4. and `ZodError.message` finally stringifies the resulting issues. (clue: `ZodError.message (packages/zod/src/v3/ZodError.ts:280-282)`)
- What File 1 does not show is the full ordering among every possible customization layer (for example, whether there are multiple stacked error maps at schema, parse-call, or global scope). So I cannot prove a complete precedence chain beyond the one explicit rule in `ZodError.format`: `issue.message` beats the default path. (clue: `ZodError.format (packages/zod/src/v3/ZodError.ts:217-264)`, `ZodErrorMap (packages/zod/src/v3/ZodError.ts:329-330)`)
