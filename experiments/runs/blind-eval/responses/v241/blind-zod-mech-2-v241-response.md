## Error Message Resolution in Zod

Zod provides multiple layers for customizing error messages. The clue file and source snippets reveal how these layers interact.

### 1. Per-Check Inline Messages

The most specific customization is a `message` parameter passed directly to a check method:

- **`ZodNumber.multipleOf`** (snippet: `packages/zod/src/v3/types.ts L1547-1554`):
  ```
  multipleOf(value: number, message?: errorUtil.ErrMessage) {
    return this._addCheck({
      kind: "multipleOf",
      value: value,
      message: errorUtil.toString(message),
    });
  }
  ```
  The optional `message` is converted via `errorUtil.toString(message)` and stored in the check definition. `ZodBigInt.multipleOf` follows the same pattern (FOCUS: `ZodBigInt.multipleOf`, `packages/zod/src/v3/types.ts:1792-1800`; behavior: `DELEGATE(this._addCheck -> result)`; `uses: errorUtil.ErrMessage, this._addCheck, errorUtil.toString`).

- **`ZodArray._parse`** shows how stored messages are used: when `def.exactLength` fails, the issue includes `message: def.exactLength.message` (snippet: L2241-2317). Similarly, `def.minLength.message` and (by pattern) `def.maxLength.message` are passed to `addIssueToContext`. If the user provided a message when calling the check method, it is emitted here.

### 2. The `addIssueToContext` Flow

- When a check fails, `_parse` methods call `addIssueToContext(ctx, { code, ..., message })` (snippet: `ZodArray._parse`). The issue object includes a `code` (e.g., `ZodIssueCode.invalid_type`, `ZodIssueCode.too_big`, `ZodIssueCode.too_small`) and optionally a `message`.
- **`RefinementCtx`** provides `addIssue: (arg: IssueData) => void` (snippet: `RefinementCtx`, L38-48). Custom refinements use this to inject issues with custom messages.
- **`CustomErrorParams = Partial<util.Omit<ZodCustomIssue, "code">>`** (snippet: L56) allows users to pass custom error data excluding the code.

### 3. The Error Map Layer

- **`ZodErrorMap`**: `(issue: ZodIssueOptionalMessage, _ctx: ErrorMapCtx) => { message: string }` (FOCUS: `packages/zod/src/v3/ZodError.ts:329-330`). This is a function that receives an issue *without* a mandatory message and an error context, and returns a `{ message: string }`.
- **`ZodIssueOptionalMessage`** is a union of all issue types (invalid_type, invalid_literal, unrecognized_keys, invalid_union, invalid_enum_value, etc.) — notably without a required `message` field (FOCUS: L151-152). The error map's job is to fill in the message.
- The naming "Optional" in `ZodIssueOptionalMessage` confirms that the message may or may not be present at this stage — it can come from the check's inline `message` or be generated by the error map.

### 4. ZodError Construction and Formatting

- **`ZodError`** (v3) extends `Error` and collects `this.issues` (FOCUS: `ZodError`, `packages/zod/src/v3/ZodError.ts:193-316`).
- **`ZodError.message`** getter: `return JSON.stringify(this.issues, util.jsonStringifyReplacer, 2)` (snippet: `ZodError.message`, L280-282). The final error message is the JSON-serialized array of all issues.
- **`ZodError.toString`** delegates to `this.message` (FOCUS: `ZodError.toString`, L277-279).
- **`ZodError.format`** has behavior `PRECEDENCE(issue -> default); ACCUMULATE(format loop -> result); TRANSFORM(map)` (FOCUS: `ZodError.format`, L217-264). This annotation reveals the precedence: **issue-level messages take priority over defaults**. The method loops over issues, accumulating them into a formatted result, and applies a mapper transform.

### 7. Resolution Priority (Inferred)

Based on the evidence:

1. **Inline check message** (highest priority): If `message` was passed to a check method (e.g., `multipleOf(5, "Must be multiple of 5")`), it is stored in the check def via `errorUtil.toString(message)` and passed directly in the `addIssueToContext` call (snippets: `ZodNumber.multipleOf`, `ZodArray._parse`).
2. **Error map**: If no inline message is present, the `ZodErrorMap` function is invoked with `ZodIssueOptionalMessage` (lacking a message) and `ErrorMapCtx` to generate one (FOCUS: `ZodErrorMap`).
3. **Default message**: The `ZodError.format` behavior annotation `PRECEDENCE(issue -> default)` (FOCUS: L217-264) confirms that issue-level data takes precedence over defaults.
4. **v4 injectable error class**: The `$Parse` `_params.Err` (FOCUS: L7-9) allows overriding the entire error class, providing a structural-level customization point.
