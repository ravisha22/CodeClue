# Supabase Deep Context

-- DOMAIN MODEL
This repository is best understood as a monorepo for the Supabase product surface, not a single service implementation. The root README defines the platform domains—Postgres database, Auth, autogenerated APIs, Realtime, Functions, Storage, AI/vector tooling, and Dashboard—while the workspace layout shows how those concerns are split across apps and shared packages. At the top level, `apps/` contains user-facing products like `studio`, `docs`, `www`, and related sites, while `packages/` contains reusable UI, config, types, and service client glue such as `common`, `ui`, `ui-patterns`, `api-types`, and `pg-meta`.

For domain analysis, `apps/studio` is the key artifact. Studio is the administrative control plane UI used both for hosted Supabase and self-hosted setups (`apps/studio/README.md`). It does not implement all backend services directly; instead, it acts as a project-scoped frontend that manages and visualizes the capabilities of underlying platform services. That distinction matters. When you see auth, storage, realtime, edge functions, or database pages in Studio, the actual engines are external or separately packaged services—GoTrue, Storage API, Realtime server, Edge Functions runtime, PostgREST, PostgreSQL, and postgres-meta—while this repo mostly holds the UI, route structure, fetchers, and shared workspace code that orchestrate them.

Studio’s internal domain model is project-centric. Most feature routes live under `pages/project/[ref]/...`, where `[ref]` is the project reference that scopes all downstream data fetching and UI state. Under that project boundary, the product is divided into database, auth, storage, realtime, functions, logs, observability, settings, API docs, SQL editor, and integrations. This means the primary business object in the frontend is “a Supabase project and its service surfaces,” not low-level entities alone.

The package structure reinforces this. `packages/api-types` gives typed API contracts to the frontend; `packages/common` centralizes shared auth/fetcher/runtime behavior; `packages/ui` and `packages/ui-patterns` provide shared design primitives; `packages/pg-meta` exposes database-management capabilities. Together these packages form the reusable layer that lets Studio treat auth users, storage buckets, edge functions, tables, or realtime settings as consistently fetched and rendered resources.

The root README also clarifies the service boundaries behind the UI. Auth is GoTrue, Realtime is an Elixir service driven by PostgreSQL replication, Storage is a REST service using S3 plus Postgres permissions, and database management is exposed through postgres-meta and PostgREST/GraphQL interfaces. So even though this repo contains the dashboard and docs, its real domain context is “a product shell over a federation of specialist backend services.”

-- API SURFACE
The API surface visible in this repo is mostly a frontend-consumption layer, not the implementation of core Supabase protocols themselves. Studio contains `pages/api/*` endpoints such as `connect`, `edge-functions`, `generate-attachment-url`, `check-cname`, `mcp`, and `platform` helpers. There are also a few App Router API routes such as `app/api/incident-banner/route.ts` and `app/api/incident-status/route.ts`. These endpoints support Studio’s own product needs—testing, proxying, utility lookups, status display, and platform integration—rather than replacing backend products like GoTrue or Realtime.

The more revealing API layer is the `apps/studio/data/*` directory. This code uses shared fetchers plus React Query to bind UI components to service endpoints. For example, `data/edge-functions/edge-functions-query.ts` fetches `/v1/projects/{ref}/functions`, `data/realtime/realtime-config-query.ts` fetches `/platform/projects/{ref}/config/realtime`, and `data/storage/storage-archive-query.ts` fetches `/platform/storage/{ref}/archive`. These query modules show the actual contract shape Studio expects from the platform and how each domain is retrieved: project-ref scoped, typed, cached, and usually wrapped in feature-specific hooks.

Because the repo depends on `@supabase/auth-js`, `@supabase/realtime-js`, `@supabase/supabase-js`, and `@supabase/pg-meta` in `apps/studio/package.json`, the API surface should be seen as layered. At the outermost layer, Studio pages and components use query hooks. Beneath that, shared fetchers and typed schemas abstract network calls. Beneath that sit backend APIs implemented elsewhere in the Supabase ecosystem. That layered client architecture is one of the main things to understand before trying to reason about feature ownership in this monorepo.

The root README expands that picture further by listing official client libraries per domain—PostgREST, GoTrue, Realtime, Storage, and Functions. In practice, the repo acts as both a product monorepo and an integration hub for those service-specific APIs.

-- ROUTING
Studio routing is highly domain-driven and mostly uses the Next.js Pages Router. Top-level pages cover sign-in/sign-up, SSO, MFA, password reset, organization views, project creation, and various supporting flows (`apps/studio/pages/*`). The critical structure sits under `apps/studio/pages/project/[ref]`, where each project-scoped capability has its own route subtree: `database`, `auth`, `storage`, `realtime`, `functions`, `logs`, `observability`, `settings`, `api`, `editor`, `sql`, `branches`, `advisors`, and integrations.

This route layout is a map of the product taxonomy. Database work lives under `database` and `sql`; runtime compute under `functions`; auth administration under `auth`; object/file management under `storage`; websocket/changefeed tuning under `realtime`; operational diagnostics under `logs` and `observability`. Routing is therefore one of the clearest ways to infer domain ownership inside Studio.

The layout system mirrors this. `apps/studio/components/layouts` contains `DatabaseLayout`, `StorageLayout`, `RealtimeLayout`, `EdgeFunctionsLayout`, `ObservabilityLayout`, `LogsLayout`, `AuthenticationLayout`, `ProjectLayout`, and many others. That tells you route groups are not just URL folders—they map to dedicated navigation shells and domain-specific UX scaffolding.

There is also a useful split between UI routing and API routing. Project pages render domain UIs, while `pages/api/*` provides supporting server-side helpers. The new App Router is used only sparingly, so the mental model for Studio remains primarily Pages Router + feature layouts rather than a full server-components architecture.

One subtle routing insight is that the repo distinguishes between “project-scoped operations” and “account/org-level access flows.” Sign-in, join, organization pages, and authorize/logout sit outside `project/[ref]`, while almost all service administration sits inside it. That boundary lines up with the broader Supabase product model: you authenticate into the dashboard first, then operate on concrete projects.

-- AUTH
Auth in this repo is best understood as “Studio’s integration with GoTrue” rather than a homegrown auth system. The root README explicitly identifies GoTrue as the JWT-based authentication API used by Supabase. In Studio, `apps/studio/lib/gotrue.ts` wraps the shared GoTrue client from `common/gotrue`, exports it as `auth`, and adds dashboard-specific helpers like `validateReturnTo`, `getUserClaims`, identity extraction, and return-path merging.

`validateReturnTo` is particularly telling. It blocks protocol-relative and external URLs, requires an internal path, constrains allowed characters, and strips base-path prefixes where necessary. This is the same class of redirect-hardening you see in security-conscious dashboards: the auth flow is designed to hand control back to internal project pages without opening redirect vulnerabilities.

`apps/studio/lib/auth.tsx` provides the higher-level auth provider and sign-out behavior used by the UI. It wraps `AuthProviderInternal`, surfaces GoTrue errors to users, and on sign-out resets PostHog, clears local storage, wipes assistant IndexedDB state, and clears the React Query cache. That cleanup sequence shows that auth is tightly coupled to client-side cached state and workspace context; logging out is not just revoking a token, it is resetting the dashboard’s local project memory.

Routing also shows auth breadth. Studio has dedicated pages for sign-in, sign-up, SSO, MFA, forgot-password, reset-password, logout, and authorization. Inside project routes, the `auth` section covers users, MFA, providers, sessions, OAuth apps, OAuth server settings, protection, rate limits, SMTP, URL configuration, and third-party auth. So auth is both a user-entry flow into Studio and a first-class managed service inside a project.

The important architectural point is that the repo itself does not appear to reimplement GoTrue’s backend logic. Instead, it provides client wrappers, UI, and management surfaces for a separately implemented auth service. That distinction is crucial when tracing bugs or ownership: a broken login page in Studio and a broken GoTrue token flow are related, but not located in the same code layer.

-- KEY WORKFLOWS
The most foundational workflow is project-scoped administration through Studio. A user signs in through GoTrue-backed flows, lands in organization/project selection, and then navigates into `project/[ref]` feature areas. Layout components provide the domain shell, while `data/*` query modules fetch the current project’s settings and resources. This creates a consistent pattern across domains: route selects feature, layout provides navigation, data hook fetches platform state, component tree renders and mutates it.

Database workflows are central in `apps/studio`. The Studio README explicitly says self-hosted Studio is mainly intended to manage database-related features such as table/SQL editors, policies, roles, extensions, replication, and API documentation. That is why database tooling has substantial dedicated layout and routing support. Packages like `pg-meta` are the connective tissue here: Studio is acting as an admin frontend over database metadata and query-management APIs rather than embedding database logic directly in the UI.

Storage workflows revolve around project-level file and bucket management. The presence of `StorageLayout`, storage pages, storage explorer components, and APIs like `/platform/storage/{ref}/archive` shows that Studio treats storage as a managed service with administrative and reporting flows. The UI is responsible for browsing buckets/files, policies, and archive/report actions, while the real file-serving and permission engine live in the Storage backend service.

Realtime workflows are similar. `data/realtime/realtime-config-query.ts` fetches project-scoped realtime configuration with defaults for concurrency, event throughput, payload size, presence limits, and suspend state. That tells you the Studio role here is operational control and observability over a Realtime service, not implementing the websocket or replication engine itself.

Edge Functions workflows are explicit too. `data/edge-functions/edge-functions-query.ts` hits `/v1/projects/{ref}/functions`, and project routes/log pages cover functions plus their logs and observability. So the repo contains the UX for deploying, listing, inspecting, and diagnosing functions, while the actual execution platform is external to Studio.

Finally, cross-cutting operational workflows are surfaced through `logs` and `observability` routes for auth, storage, realtime, edge functions, database, and PostgREST. This is strategically important: Supabase Studio is not just CRUD admin UI. It is a unified operations console over multiple backend products, which is why the route map, layouts, and typed data hooks matter so much. They are the mechanism that turns a collection of independent open-source services into a single coherent developer platform experience.
